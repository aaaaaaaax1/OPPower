# OPPower 设计与运行规范

## 1. 产品目标

OPPower 在 realme Neo8 RMX8899、ColorOS 17、真实亮屏且 AC 在线时，通过 Shizuku 写入系统持久设置 `cosa_ctc_value`，把 OPPower 按热控基础档与 `cosa` 计算的 gear 调整到目标档位。总开关开启后，用户划掉界面或把应用放到后台，前台服务仍继续控制；拔电、关闭该模式或达到安全阈值时恢复系统默认。主页面另有一个独立于总开关的“高功率保活”开关，即使“强制亮屏快充”总开关关闭，只要该开关开启且满足接电条件，控制服务仍会运行。

成功标准是外接功率计显示持续且可复现的功率，不使用单次冲高、LV 循环补发、冻结 Athena/Battery、分屏、旁路充电、伪造温度或停用原生热保护。

温度降档、恢复、暂停和规则判断统一使用 OPPower 自己显示的电池温度。该温度来自 Android 电池广播的 `BatteryManager.EXTRA_TEMPERATURE`，界面、通知、记录和控制器共用同一个 `BatterySnapshot.temperatureC`，不会混用前台应用热控文本或厂商内部温度。

曲线处理与 LLPower 一致：原始记录最多保留 24 小时，可视历史为最近 8 小时，默认显示 2 小时；充电亮屏每 3 秒、充电熄屏每 5 秒、未充电每 180 秒采样。功率使用 30–90 秒聚合、稳健中心值、向上峰值保留、9 点平滑和尾部稳定；温度使用 60 秒聚合、孤立抖动修正和 7 点三角平滑。超过 7 分钟的间隔会拆成独立线段，功率纵轴按 10 W 步进，温度纵轴至少覆盖 5°C。两条曲线保留 OPPower 自己的界面样式，并可分别拖动。
为支持长时间充电，SQLite 仍保留 24 小时原始采样，但进程内曲线只保留最近 8 小时。当前会话使用增量累计器，不再在每个新采样点重建整段记录；历史充电记录统一按相邻采样的实际时间间隔做梯形加权，功率、电流、温度和充入 mAh 共用这一规则。超过 5 分钟的空档不参与平均值与积分，正常未充电的 180 秒采样仍计入。记录模型只保存统计摘要，不重复保留整段原始点。

## 2. 闭环控制

控制目标是让 OPPower 自己计算的 gear 达到规则选出的目标档位。应用不使用 `policy.gear` 缓存作为当前档位，也不使用它计算或校准目标：

```text
计算 gear = 热控基础档位 + cosa_ctc_value
热控基础档位 = getThermalStatus 的 Thermal Levels[0]
所需 cosa = 目标 gear - 热控基础档位
```

控制器在每个 1 秒周期重新读取 `cosa_ctc_value` 和 `Thermal Levels`，直接计算当前 gear。基础热控档位变化时，立即按新基础档计算新的 `cosa`，再得到新的计算 gear，不需要切换应用，也不先写 `cosa=0`。目标变化、首次开启或检测到外部把 `cosa` 改错时，当前周期直接写入计算值并回读。 `getCurThermalPolicy` 中只用于诊断的 `chargeVal`/`speedChargeAdd` 最多缓存 3 秒，不参与 gear 计算；`cosa` 与 `Thermal Levels` 仍每秒核对，因此不会降低基础档变化、目标切换、接电和设置变化后的响应速度。

常规 gear 模式不调用 `OplusBatteryService setChargingLevel`，也不发送 `set_charge(0,-2)` 广播。该广播接收器要求发送方持有 `oplus.permission.OPLUS_COMPONENT_SAFE`；Shizuku/ADB 只有 shell UID，命令即使返回 `Broadcast completed` 也没有送达接收器，实际不会进入 `D1()`。普通控制会话只保留“写 `cosa` → 回读 → 触发一次热控重算”。

2026-11-22 新增、2026-11-23 修正为真正独立于总开关的“高功率保活”（内部使用 `setChargingLevel 0`）是默认关闭的显式 opt-in 模式，不在常规 gear 规则内。界面名称下显示“（强制亮屏快充不行再试试这个）”。开启后即使“强制亮屏快充”总开关关闭，控制器仍先恢复 `cosa=0`，再立即并最多每 3 秒一次下发 `setChargingLevel 0`；不读取温度分档、不写普通 gear 目标，也不经过 `RuleEngine` 选档。关闭总开关不会停止保活；80% 本次暂停、100%/FULL 暂停、拔电、关闭保活（且总开关也未开启）或息屏暂停时，先下发安全级 `setChargingLevel 2`，再恢复 `cosa=0`。系统原生温度保护继续运行。白名单只允许 `setChargingLevel 0` 和 `setChargingLevel 2`，其他档位及拼接命令仍拒绝。

二级页“息屏也生效”默认关闭。关闭时屏幕熄灭会暂停全部充电增强并执行上述安全恢复；开启后，普通快充和高功率保活都允许在息屏时继续。该开关只决定是否因息屏暂停，不改变 80%、充满、拔电和 Shizuku 可用性保护。

Beta17 起，OPPower 不再读取或写入 GuardElf `SmartChgMode`。beta8 在只写 `cosa`、只触发一次热控重算时曾持续约 7 分钟达到 30 W 以上；后续加入 `SmartChgMode=0` 改变了这一自然策略条件，并带来额外 Binder 写入。当前常规控制会话只包含目标 `cosa` 的写入和一次热控刷新。

`getCurThermalPolicy` 的 `gearVal` 缓存不参与控制、显示和验收；代码只从中读取 `chargeVal` 作独立诊断。即使 `policy.gear` 仍是旧值，也不会影响 OPPower 的 `基础档 + cosa` 结果。`chargeVal` 不参与 gear 求和。2026-10-26 源码复核确认：原始 `policy.charge=-2` 在系统 `HeatSourceController.e()` 中会归一化成充电 level 0，再交给 `D1()`；它本身不等于 HAL 已生效。页面 `chargeVal=--` 仅表示诊断读取缺失，不能把它等同于 `-2` 或 cooldown 0（详见操作书 34.3）。热控复杂场景可能把同一个计算 gear 0 映射成 `chargeVal=12, speedChargeAdd=0`，因此 OPPower 不把回读的 `chargeVal` 当作 gear 计算依据，也不会用另一条原生充电命令覆盖热控结果。

界面显示 `基础档 + cosa = 计算档位`，并单独显示 `chargeVal`。`cosa` 回读成功且计算结果等于目标后即标记达到目标。

写入 `cosa` 后触发一次系统热控重算。优先监听 `oplus_float_window_show`：其回调调用 `m.j2(null, 0ms)`，立即提交策略重算。OPPower 把该设置的同一整数改成等价字符串写法（`0 ↔ 00`、`1 ↔ 01`）来触发监听，数值保持不变。Provider 没有该行时读取结果为 `null`；系统只把整数 `1` 当作浮窗场景，`null` 和 `0` 都是非浮窗状态，因此控制器把 `null` 规范化为 `0`，既保持策略语义，也能触发同一条即时回调。若即时入口不可用，才回退到 `oplus_camera_3rd_activity`；相机回调最终调用 `m.m2()`，内部约 5 秒后计算。两条路径都只触发一次，不在应用侧等待。

beta20 起取消自动 gear 1 保护。目标为 gear 0 时，控制器始终按“基础档 + cosa = 0”立即下发并刷新，不因温度自动改写目标。电池功率使用与 LLPower 相同的 `BatteryManager.getLongProperty(CURRENT_NOW)`，仅当它返回 0 时回退到 `CURRENT_AVERAGE`。页面 1 秒采样与历史数据库写入分离，单次采样或写库异常不会终止刷新循环。

beta27 已按用户要求撤销 `smart_charge_switch_state` 补充提升。当前版本不读取、不写入、不持久化该设置，也不再向 Shizuku 暴露对应命令；控制会话只维护 `cosa_ctc_value`，因此不会把用户恢复的系统智能充电值 `1` 再改回 `0`。设置页的系统通知权限、通知渠道、电池优化、悬浮窗、无障碍和 Shizuku 连接状态仍从 Android 与 Shizuku 实时读取，并在启动、恢复前台和授权回调后刷新。

beta22 将电池电流读取顺序与 LLPower 对齐：先 `CURRENT_NOW`，再 `CURRENT_AVERAGE`，最后尝试 `/sys/class/power_supply/.../current_now` 等节点；无效哨兵归零，只有绝对值大于 20000 时才按微安换算。该机快充时 `CURRENT_NOW` 约为 `±9,500..±10,100` mA，旧实现的 10000 阈值会把越过阈值的一帧错误除以 1000，导致界面在约 38 W 和 0 W 之间跳动。功率由同一电流与电池电压直接计算，电流和功率使用同一修正结果。

`cosa_ctc_value` 的可用范围从 beta23 起为 `-10..9`。基础档为 10、目标 gear 为 0 时写入 `-10`；基础档继续高于 10 时目标不可达，控制器保持在 `-10` 安全下界并明确显示实际计算档位。历史版本曾把 `-10` 视为无效哨兵，beta23 按当前设备实测需求调整下界；`-11` 及以下仍禁止写入。
beta24 起，基础档“最大输出”不再执行 OPPower 自身的 41/42/43°C 温度分档，也不因温度切到 gear 1 或暂停；只要未达到 80% 电量暂停点，目标始终是 gear 0，温度变化只由系统原生热控处理。2026-10-25 真机已观察到基础档从 10 升到 11；此时 `cosa=-10` 已到合法下界，计算 gear 为 1，界面应明确显示目标 gear 0 不可达并保持 `-10`，禁止为了追求 gear 0 写入 `-11`。`getCurThermalPolicy` 返回 `null` 只代表当前策略回读为空，不能据此认定原生热控失效。

beta25 修复“OPPower 偶发显示 0 W、LLPower 和充电器仍正常”的采样问题。历史库确认 AC 在线时原样记录过 33 条 `current_ma=0`、`power_w=0`，持续 3–30 秒；同期电压、温度、SOC 和充电状态正常，根因是 `BatteryManager.CURRENT_NOW` 本身偶发返回 0。应用现在只在 AC 在线、SOC 小于 99%、状态不是 FULL，且主电流为 0 或电压无效时，通过 Shizuku user service 执行一次固定只读 `dumpsys battery`，从同一输出取得 `Battery current` 与 `voltage` 后作为一个完整采样使用。后备值缺失、为 0 或超出合理范围时先由短时纠错器复用最近可靠帧；该复用只适用于 AC 在线且未充满的偶发零值，最多 3.5 秒，之后立即接受真实 0。正常非零功率变化不做平滑或防抖。普通页面和前台控制服务共用该策略。

最大输出默认不再使用 41/42/43°C 三段规则，40.0–45.8°C 单测目标均为 gear 0；温度只影响系统原生 `Thermal Levels[0]`，OPPower 随后按新的基础档重算 `cosa`。20–40 W、10–30 W、80% 电量暂停、100%/FULL 暂停和显式自定义规则保持不变。

RMX8899 的下表只记录“基础档为 8、场景其他影响当时为 0”时的历史条件样例。控制实现不使用该表中的固定映射：

| `cosa_ctc_value` | 当时系统 gear | `chargeVal` | 结果 |
| ---: | ---: | ---: | --- |
| `0` | 8 | 2 | 原生约 5 W |
| `-3` | 5 | 4 | 开始提升 |
| `-4` | 4 | 6 | 约 10–14 W |
| `-6` | 3 | 7 | 更高 |
| `-7` | 2 | 9 | 更高 |
| `-8` | 1 | 9 | 接近最高输出 |
| `-9` | 0 | 12 | 实测约 15–30 W，跨应用保持 |
| `-10` | 0 | -2 | beta23 起用于基础档 10 时保持 gear 0；beta24 已真机确认自动写入并维持 |
| `-11` 及以下 | 0 | -2 | 无效哨兵，禁止使用 |

例如基础档为 6、目标为 0 时，所需 `cosa=-6`，计算结果也是 gear 0。基础档变成 7 后，目标仍为 0 时立即改为 `cosa=-7`。

常规 gear 模式只有拔电、关闭总开关、电量暂停、充满或用户点击“一键恢复”才恢复系统默认 `cosa=0`；高功率保活独立判断自身开关，不能因为总开关关闭而恢复。实际写入时触发一次系统重算。系统驱动的服务销毁和重建不属于恢复条件；服务保持已持久化的控制意图，并在重建后继续计算目标。普通回读异常、短时策略为空或一次重算触发失败只保持当前偏移并继续读取，不会先把功率清零。软件不读取、不写入 `single_speed_charge_state`。

## 3. 用户档位

| 用户档位 | 内部 gear | 本次实测参考 |
| --- | --- | --- |
| 最大输出 | 0 | 系统当前允许的最高输出，不写预估瓦数 |
| 20–40 W | 1–4 | gear 1 约 35–40 W；gear 2 约 25 W；gear 3/4 约 20 W |
| 10–30 W | 2–5 | gear 2 约 25 W；gear 3/4 约 20 W；gear 5 约 11 W |

实测只覆盖抖音极速版真实亮屏前台和当时充电器、温度、电量条件。gear 3 与 gear 4 同段，gear 1 与 gear 2 之间存在大跨度，不能把 gear 当线性功率刻度。

## 4. 页面

### 主页面

- 标题左侧功能入口为“加入 QQ 群”，设置图标位于右侧。
- 当前功率、电流 mA、电压 V、温度、电量、电池状态、供电方式。
- 充放电记录摘要，以及上下分开的功率曲线、温度曲线；横轴为系统时间。
- 原始记录最多保留 24 小时；可视曲线显示最近 8 小时，默认显示 2 小时窗口，并可分别左右拖动，横轴每 15 分钟一个时间节点。
- 图表内容保持清晰、克制的网格和两种数据色；外层与全应用统一采用液态玻璃容器、主题色边缘高光和柔和阴影，避免装饰遮住数据。
- 始终显示“强制亮屏快充”卡片及主开关，点击进入详细设置。
- 页面数据每秒刷新一次；功率和温度曲线使用 LLPower 采样节奏：充电亮屏每 3 秒、充电熄屏每 5 秒、未充电每 180 秒。界面关闭或划掉最近任务后，前台服务仍继续积累曲线，原始记录最多保留 24 小时。
视觉层采用克制的深色液态玻璃体系：页面背景是低对比的深青纵向渐变，仅保留一处很淡的冷色柔光，不使用彩色光斑、漂移光带或整面白雾；卡片使用半透明深色填充、发丝级高光边、主卡片左上角的局部反光与柔和投影。玻璃层次通过透明度、边缘亮度和阴影表达，背景保持静止，避免装饰和动态光效干扰读数。页面层级、控件位置、点击区域和字体比例逻辑不变，主题切换会同步更新玻璃层次、阴影、强调色和浅色/深色对比。

### 强制亮屏快充二级页

- 总开关与一键恢复。
- Shizuku 权限状态。
- 三个基础档，以明显描边、底色和“已选择”标识突出。
- 默认规则展示明确写出 `<`、`≤`、`≥` 区间。
- 自定义规则固定保留两条温度条件和两条电量条件，使用弹出数字键盘输入，不显示上下加减按钮。
- 温度条件支持 0.5°C 精度和 30.0–46.0°C 范围；每条温度条件可直接选择最大输出、20–40 W、10–30 W 或暂停。
- 电量条件支持 1–100%；电量只切换大档，不参与功率档内部的温度分档。
- 每行使用紧凑输入框和真正的下拉菜单；编辑后动态显示当前区间、档内 0.5°C 温度分段和严格边界说明。
- “读取档位”按钮只读 `Thermal Levels[0]` 和 `cosa_ctc_value` 后计算档位，不要求控制服务正在运行，也不写入任何设置。

### 应用设置页

右上角设置使用多级页面，入口与行为按 LLPower 设置分类独立实现：

- **外观设置**：跟随系统、浅色、深色；六种主题配色；字体与界面比例；卡片不透明度；隐藏最近任务。主题与比例立即应用到 Compose 界面；隐藏最近任务只影响任务栏显示，不停止控制服务。
- **稳定运行**：检查通知权限、电池优化、悬浮窗与无障碍服务，提供系统权限入口，并显示当前控制状态。
- **通知设置**：状态通知开关、通知内容字段、亮屏/熄屏刷新间隔、充满与熄屏自动精简和系统通知权限。只要接电就显示状态通知，无论亮屏快充总开关是否开启；总开关开启时正文首项显示当前用户档位，关闭时显示“亮屏快充未启用”。Android 16 与 ColorOS 17 使用与 LLPower 相同的 `Notification.ProgressStyle`、`battery_live_update_v2` 实时通道、`setOngoing(true)` 和 `android.requestPromotedOngoing`；缺少常驻标志时 ColorOS 会退回带应用图标的普通通知卡。必须在系统“OPPower 通知设置”中开启“流体云显示实时活动”，设置页提供该入口。启用后使用系统透明实时卡片，不显示可见应用图标、收放箭头、额外“打开 OPPower”操作行或“本次关闭”按钮，并在正文末尾显示亮屏快充档位。
- **高级保活**：可选的 1×1 透明悬浮窗与无障碍保活。悬浮窗不拦截触摸；无障碍服务不读取屏幕内容，也不执行自动点击。
- **硬件修正**：反转电流方向、双芯电流修正、虚拟电压和绝对值显示。修正用于当前显示、通知和曲线输入，不改写系统电池数据。
- **系统与诊断**：电池优化、应用详情和 Shizuku 授权入口；Shizuku 未安装、未运行、未授权和已授权四种状态均可操作。调试模式只显示用户可理解的状态、功率档、充电状态、电源接入与授权结果。
- **数据管理**：本地占用、24 小时原始曲线记录、充放电摘要数量、曲线开关和确认清除。
- **常见问题、关于、重要说明、开发者说明、开源许可**：说明功率差异、原生温控边界、来源、数据本地化及第三方依赖。

LLPower 的灵动岛、壁纸库、启动图标切换和语言切换依赖其独立资源与服务，当前版本不显示这些空入口。桌面组件仍属于后续功能。

## 5. 默认规则

自定义关闭时，基础档“最大输出”没有 OPPower 自身的温度阈值。未达到电量暂停点时，无论电池温度处于 41/42/43°C 或更高，计算目标都持续为 gear 0；系统原生热控仍独立调节 `Thermal Levels[0]`，OPPower 只按新的基础档立即重算 `cosa`。基础档超过 10 时，受 `cosa=-10` 安全下界限制，计算 gear 可能暂时大于 0，应用显示“目标不可达”，不会写入更低的数值。

基础档 20–40 W 或 10–30 W 时，`T < 43.0°C` 在自身 gear 集合内按温度选档；`T ≥ 43.0°C` 暂停 gear 策略。开启自定义规则后，两条温度条件和两条电量条件按用户输入生效，并可显式选择最大输出、20–40 W、10–30 W 或暂停。

电量规则独立于内部 gear：

| 条件 | 行为 |
| --- | --- |
| `SOC ≥ 80%` 且 `< 100%` | 本次插电暂停 gear，`cosa=0`，温度回落也不恢复 |
| `SOC = 100%` 或状态 FULL | `cosa=0`；总开关仍保留用户选择 |

拔电时恢复 `cosa=0`。再次接电时直接读取当前 `cosa` 和 `Thermal Levels`，按 `基础档 + cosa` 立即建立计算档位；若 SOC 仍达到暂停点，则立即暂停。软件不修改 `single_speed_charge_state`。

## 6. 自定义规则

自定义规则由两条温度条件和两条电量条件组成。每条温度条件有阈值和目标档位，界面允许用户填写阈值，并实时展示实际区间：

```text
T < T1                         → 基础档
T1 ≤ T < T2                   → 温度条件 1 的目标
T ≥ T2                        → 温度条件 2 的目标
```

温度条件按从低到高执行。为避免更高温度反而提高功率，规则引擎只接受“与当前档相同或更保守”的目标：

```text
最大输出 > 20–40 W > 10–30 W > 暂停
```

例如基础档为最大输出，41°C 可选 20–40 W；随后 42°C 只能继续 20–40 W、降为 10–30 W 或暂停。规则引擎会保持更保守的结果，即使界面输入了一个会反向升档的组合。

温度条件范围 30.0–46.0°C，至少间隔 0.5°C。保存时会限制并稳定排序，避免无效区间。电量条件同样必须严格递增。

## 7. 动态档位与温度

- 最大输出只有 gear 0 一个目标，OPPower 不再按温度分档；系统原生热控通过改变基础档影响所需 `cosa`，但不会让应用主动追求升温或更高功率。
- 20–40 W 大档内部按 0.5°C 分段，从本档实测 gear 集合等距选择；温度越低使用越高功率端。
- 10–30 W 均衡档内部只看温度；电量只决定是否暂停整个 gear 策略。
- 用户选择基础档、修改自定义规则或切换目标时不做防抖；当前控制周期按“目标 − 基础档”动态计算目标 `cosa`，只写一次并触发一次系统重算。
- 计算 gear 只由 `Thermal Levels[0] + cosa` 得到；`policy.gear` 缓存不参与计算或验收，`chargeVal` 只显示为诊断字段。常规目标保持期间不重复写入 `cosa`、不重排 `m2()`，也不调用原生 `setChargingLevel`；只有用户显式开启高功率保活时才走独立的 3 秒复写路径。
- 暂停策略、SOC 锁定与 100% 充满规则优先于温度恢复。
- 原生热保护持续运行，应用不会伪装或关闭温度来源。

## 8. 后台与恢复

前台服务负责采样、状态通知和唯一一次设置写入。界面只更新共享状态，避免界面与后台重复写同一设置。

- 常规 gear 模式下，AC 在线时前台服务每 1 秒读取基础档和 `cosa` 并重算档位；基础档变化、目标变化或外部 `cosa` 漂移时写入一次。页面数据每秒刷新，曲线按 LLPower 的 3/5/180 秒节奏采样。AC 断开后恢复 `cosa=0` 并释放前台服务，下一次接电由电源广播立即建立新会话。
- 用户划掉界面后服务继续运行，主开关保存于 SharedPreferences。
- 常规 gear 模式关闭总开关、AC 断开、SOC 暂停或充满时恢复 `cosa=0`；若高功率保活仍开启，关闭总开关不会中止该独立路径。关闭最后一个充电增强开关时，服务必须先完成安全级恢复再退出。系统销毁服务属于后台生命周期事件，不能据此撤销已下发的控制意图：`START_STICKY` 重建后继续按当前开关和基础档计算并保持目标。
- 服务启动时先读取设备当前 `cosa`；正常启用和切换都直接覆盖 `cosa`，不先清零，也不依赖持久基础档。
- Android 无法保证进程被强制终止或 Shizuku 停止后的即时回滚；界面与文档保留这项限制。
- 插拔电广播会立即唤醒控制服务；屏幕开关广播控制熄屏刷新频率、自动关闭和亮屏恢复。
- 状态通知在接电时存在，仅开启高功率保活时显示对应保活状态，即使总开关关闭也不会显示“未启用”；拔电或通知功能关闭时撤掉。Android 16 及以上使用 `Notification.ProgressStyle`、`battery_live_update_v2` 通道、`android.requestPromotedOngoing` 和 `POST_PROMOTED_NOTIFICATIONS` 对齐 LLPower 的实时活动卡片；ColorOS 的“流体云显示实时活动”关闭时系统会拒绝提升，必须由用户在 OPPower 的系统通知设置中开启。旧系统保留普通通知和 `android.app.preferSmallIcon` 兼容路径。
- 通知栏不再提供“本次关闭”动作；普通快充、高功率保活分别通过各自开关或一键恢复关闭。
- 不启动独立 shell 看门狗，不加入高频或低频守门轮询。常规控制器只在目标、基础档或外部偏移变化时写入并触发一次热控重算；稳定期间只读，AC 断开后恢复并退出。高功率保活是唯一例外，按 3 秒节流重发其固定保活命令。

## 9. Shizuku 与权限

设置主页、亮屏快充详情页和系统页均提供 Shizuku 授权入口。未安装时打开官方下载页；未运行时打开 Shizuku；服务运行但 OPPower 未授权时发起权限请求；授权后绑定 user service。应用使用 Shizuku user service 和 AIDL 接口执行以下白名单命令：

```text
settings get global cosa_ctc_value
settings put global cosa_ctc_value -10…9
settings get system oplus_camera_3rd_activity
settings put system oplus_camera_3rd_activity 0|1|00|01
settings get system oplus_float_window_show
settings put system oplus_float_window_show 0|1|00|01
dumpsys activity service com.oplus.battery/.OplusBatteryService getCurThermalPolicy
dumpsys activity service com.oplus.battery/.OplusBatteryService getThermalStatus
```

`readBatteryFallback()` 是独立的只读 AIDL 方法，固定执行 `dumpsys battery`，不接受调用方传命令；user service 内部超时 1.5 秒，主进程等待服务绑定最多 350 ms。它只在上述伪零条件触发，不扩大任意 shell 权限。LLPower 2.0.4 实际有两条采样路径：`BatteryEngine` 使用 `CURRENT_NOW → CURRENT_AVERAGE → current_now/main current_now/batt_current`，`ChargeEngine` 在 sysfs 缺失时解析 `dumpsys battery`；OPPower 按同样顺序组合这两条只读路径。

不接受任意 shell、分号拼接、命令替换或其他设置名。`oplus_float_window_show` 与回退入口 `oplus_camera_3rd_activity` 只允许 `0/1/00/01` 四种等价写法，用于数值不变的监听触发；浮窗设置缺失时由控制器注入一次 `0`。`setChargingLevel` 只允许完整的 `0` 和恢复安全级 `2` 两条固定命令，其他档位和拼接形式拒绝；`SmartChgMode` 和 `set_charge` 广播仍不在白名单。除 Shizuku 自身授予的能力外，不绕过签名、SELinux、HAL 或 OEM 组件权限。

## 10. 当前限制

- 只在 RMX8899 / ColorOS 17 的已知固件路径上设计和实测。
- `getCurThermalPolicy` 的 `gearVal` 可能短时返回空值或旧值；该字段不参与控制，OPPower 始终使用基础档和 `cosa` 的计算结果。`chargeVal` 读取失败只影响诊断显示。
- 跨应用、低电量、高电量、不同温度与不同充电器的功率映射仍需继续标定。
- 桌面组件为后续功能，当前界面没有展示入口。
- 当前 beta APK 使用 Android debug key 签名，并已安装到真机；完整充电功率验收仍需继续。每个版本归档到 `release/<versionName>/`，禁止覆盖旧版本；正式发布必须更换独立 release keystore。
